Renderer troubleshooting

The same notes are in docs/troubleshooting.md in the repo. The viewport status label names the backend that actually started. The short git revision on that label is this page's build. GET /api/health returns the API's build.revision.

What the status label means

Starts withMeaning
WebGPUReal WebGPU device
WebGPU (WebGL2 fallback: …)three's WebGPU renderer is on its WebGL2 backend
WebGL (WebGPU unavailable: …)WebGPU was requested and a classic WebGL renderer is drawing. The reason is in the parentheses
WebGLThis session asked for WebGL, or the page is older than this label

?renderer=webgpu-strict shows the reason and does not fall back. ?renderer=webgl forces WebGL.

Plain WebGL that cleared after a restart

A stale bundle constructs WebGLRenderer and the old label was the literal WebGL, even when the adapter was fine. That is a cached module, an old frontend/dist, a build:webgl bundle, or a Vite prebundle of three (that file is three.module.js, which exports WebGLRenderer). three.webgpu.js does not.

Starlette used to serve frontend/dist with ETag and Last-Modified and no Cache-Control, so the browser could keep index.html. Restarting the API does not rebuild dist. Hard-reload, then compare the status revision with /api/health. A banner that says the server is older means restart scripts/dev.sh (API and Vite). A banner that says this page is older means the bundle is stale: hard-reload, and rebuild frontend/dist if the Python server is what you opened. index.html is now no-cache. Fingerprinted files under assets/ stay cached.

three r170 also hides the original WebGPU error. A null adapter or a failed requestDevice makes it swap in a WebGL2 backend and continue. Forge records that reason instead of leaving the line as plain WebGL. Missing texture-compression-bc does not block startup. A device lost after WebGPU has started leaves the line on WebGPU and shows a toast.

Brave Shields and the WebGPU flag

  1. Open brave://flags/#enable-unsafe-webgpu and set it to Enabled. Relaunch.
  2. Shields for this site can still hide the adapter. Lower Fingerprinting blocking, or turn Shields off for 127.0.0.1. The line then says adapter is null or requestDevice failed: ….
  3. Open brave://gpu (Chrome: chrome://gpu). WebGPU should be Hardware accelerated.

Linux

WebGPU on Linux goes through Vulkan. If the GPU page shows it unavailable, launch with --enable-unsafe-webgpu. If Vulkan is disabled there, add --enable-features=Vulkan or --use-angle=vulkan. Some Brave builds have brave://flags/#enable-vulkan. Driver problems on that same page (old Mesa, missing NVIDIA Vulkan ICD) fail the adapter before Forge runs.

Check from the console

navigator.gpu
const adapter = await navigator.gpu.requestAdapter()
adapter && (adapter.info || await adapter.requestAdapterInfo())
const device = await adapter.requestDevice()

navigator.gpu undefined means the API is hidden. requestAdapter() returning null is the no-adapter / Shields case. A throw from requestDevice() is the message on the status label. Forge also logs code, adapterInfo, and limits.
